## 1. Wiki feeding skills
Real or local: Automated skill optimization is local to WikiSkill's measured task environment. Learning from the wiki is already possible here: Ingest step 5 routes implications into a separate structural change, and Version control requires a branch, draft PR, and explicit merge approval. The missing benchmark is a reason not to automate acceptance, not a reason to prohibit informed improvements.

Smallest change: No schema or skill change. Let wiki findings motivate a separately reviewed skill patch through the existing workflow and vendoring owner. For a concrete patch, cite the motivating wiki page and raw source in the PR, state the intended behavior, and demonstrate it on a representative task plus a relevant failure case. Run the required lint and template matrix; these check integrity, not skill effectiveness. Human review remains the acceptance gate, with a revert available if actual use regresses.

Per-skill provenance is useful only when there is an actual derivation to explain. Keep that explanation in the change's PR or decision record, not a mandatory PURPOSE.md beside every vendored skill. Instance-specific wiki links inside portable skills would add local dependencies and upstream divergence; upstream pinning and local design rationale are different provenance needs.

No change to MCP readers. Section 5.1 tests wiki access during skill-development rollouts, using one model and four benchmarks; its outcome is final skill quality. It does not test whether ordinary knowledge consumers answer better with the wiki. Both the Maintainer and Proposer read it; it is not maintainer-only. Restricting read-only product clients would defeat this MCP surface's purpose without supporting evidence.

Cost: Zero extra work on ordinary ingests beyond the existing implication note. A proposed skill change pays for evidence and behavioral review once. Obsidian readers retain a linked explanation without a second catalog of skill-purpose pages. Mandatory PURPOSE files would instead create upkeep on every relevant skill or page change, without a score to justify the machinery.

## 2. Evidence anchors
Real or local: Evidence-version invalidation is local to OpenWiki's changing repository evidence. Locating a supporting passage in a long immutable paper is a real reader cost here. Immutability prevents a correctly written locator from drifting; it neither makes an initially wrong locator correct nor prevents newer sources from challenging the claim.

Smallest change: A convention in AGENTS.md Claims: “For new or substantively revised claims, optionally link to an existing source heading when it materially narrows the evidence; otherwise cite the file with a short quotation or section label. Never edit raw files to create anchors.” This explicitly relaxes the stated file-only prior convention. Use existing block IDs only if already present and useful. No blanket backfill; improve a citation when auditing that claim.

Do not add anchor lint now. The current WIKILINK_RE discards the fragment; check_claims checks for at least one resolving target, and check_raw_refs checks existence. None verifies a heading, a passage, or entailment. Manually verify each anchor added; do not describe today's successful lint as anchor validation. Duplicate headings, converted source headings, and PDF evidence make universal anchor requirements costly. Revisit a narrowly scoped checker if broken anchors actually recur.

Cost: A small optional lookup during a relevant ingest, no migration across existing claims. Readers can jump to evidence rather than search an entire paper; aliased links can keep the callout compact. Mandatory anchors would impose this lookup on even short sources, while custom anchor insertion would violate raw immutability. A new parser would add maintenance without checking whether the cited passage supports the assertion.

## 3. Scheduled capture
Real or local: A future authority boundary is real, but unattended capture is not currently authorized. AGENTS.md already says slash workflows are user-invoked and never fired autonomously. Scout's disable-model-invocation flag and interactive approval step agree. Do not infer timer permission from its state model.

Smallest change now: No change is required. If an explicit sentence is wanted, put it within the insight feature markers: “Scheduled scout runs and unattended capture are not authorized by this schema; they require a separately reviewed workflow change.” Do not install a scheduler or redesign capture preemptively.

If scheduling is actually requested, authorize discovery and staging first. State the following contract in AGENTS.md and mirror its execution details in the scout skill:

- The scheduled run may append a completed candidate/failure run section only to staging/scout.md, carrying unresolved candidates and watch proposals forward. It may not approve rows, change human decisions, capture raw files, update staging/ingest.md, edit wiki/config/schema/skills, commit, or ingest.
- The human gate is an explicit approval of identified ledger rows, followed by an interactive capture invocation. A prior approval is not permission for the timer to capture. No PR is needed for each candidate: the ledger is already the review surface. The workflow-enabling schema change itself still needs its draft PR and merge approval.
- Interactive capture rechecks the selected source and approval, creates a new immutable snapshot, verifies the saved file, then marks the row captured and queues it for ingest. A failed or uncertain save must not advance the row to captured; reconcile a retry against any existing file before writing again.
- Read preferences afresh and stop if unavailable. Preserve failed-source windows and record incomplete coverage. Advance state only after the result is durably staged. Serialize runs so a timer cannot overwrite concurrent human review.

Before enabling that mode, fix scout's cursor semantics: a run-header date is not the source's newest successfully read item. A newly introduced watch entry has no proven prior coverage; consecutive failures need the recorded start window, including a defined first-run fallback. A source returning only a bounded result set is not necessarily fully read. Keep these details in the skill/state, with instance settings in kb.toml, not hard-coded tooling.

Cost: No additional ingest or Obsidian burden now. A future staging-only timer adds a bounded review queue, failure lines, and operational supervision; capture and the one-source ingest discussion still cost human attention. Automated capture plus PRs would add another review system without eliminating source selection or interpretation work.

## 4. Missed
- **Evidence existence is weaker than provenance.** check_claims accepts a resolving wiki link, not necessarily a raw source; check_raw_refs accepts an existing path without enforcing that it lies under raw/. Neither checks the relationship between frontmatter provenance and claim evidence. This is a more basic enforcement gap than anchors. A future raw-target check must distinguish source-supported claims from speculative premises that legitimately cite wiki pages; do not silently outlaw the latter.
- **Completion must mean durable output.** OpenWiki persists and proves page state before marking completion; Anthropic records delivery only after confirmation. For capture, the transferable rule is verify the file before recording captured status. This is separate from the human approval gate: permission does not prove successful output.
- **Memory does not enforce authority.** Anthropic explicitly says planted instructions can contaminate retained notes despite read-only preferences. A writable ledger's word “approved” is not independently trustworthy authorization. Any future timer needs actual write restrictions and a human-controlled approval path, plus run/spend limits and visible failure reporting in its deployment. Prose alone cannot supply those controls.
- **Keep failed intervention evidence.** WikiSkill retains the wiki when a skill proposal is rejected and records outcomes programmatically. The useful transfer is preserving a rejected proposal's rationale in the existing PR/decision history, not creating a new impact tracker. No added per-ingest bookkeeping is warranted.
- **Read-only is not a read allowlist.** mcp/server.py's direct read_page path permits any file resolving inside the repo, beyond wiki/ and raw/; _search_dirs also accepts an existing directory supplied as scope rather than enforcing its documented enum. This does not imply excluding inference agents. If a narrower public surface is intended, enforce that boundary separately rather than treating “read-only” as equivalent to “wiki-only.”

## 5. Misread
**Skill Evolution:** “The executing agent should not read the wiki; only the maintainer and proposer should”. This supported claim title universalizes a training ablation. Section 5.1 supports the narrower finding that granting the training-rollout agent access reduced final average skill performance in this experiment; the proposed mechanism is explicitly a hypothesis. Preserve that distinction and do not infer an MCP reader policy. The passage “Relevant to any wiki with more than one kind of reader: who gets to read it is a design variable” is a broader inference, not a measured source conclusion.

**Provenance Tags:** “Facts from connectors, which have no version to pin, get no claims at all.” The README states that connector-derived facts are currently outside Grounded Claims. It does not establish that connectors have no versionable evidence or that this is the reason for the exclusion. Delete the causal clause or mark it as an inference with evidence. Also, “That third question only exists because its raw layer is versioned and changes” is too exclusive: immutable captures can become outdated accounts of the world. Distinguish evidence-byte currency from claim currency.

**Unattended Agent State:** “The one leak is that `/scout` appends approved `watch` entries to `kb.toml` itself, with the user's approval in conversation rather than through a proposals file the user applies.” This is contradicted by the current skill, which never writes kb.toml. Likewise, “`/scout`'s fan-out has no such rule: a sub-agent that could not reach its `watch` entry returns no candidates, and the merge step cannot tell that from nothing new” is stale: step 3 explicitly requires unreachable and step 4 preserves it. Label these passages as historical or update them; the later paragraph does not make their present-tense wording accurate.

**Unattended Agent State:** “The claim stays as written because the schedule it is about does not exist; what it now predicts is that these two rules are sufficient, which only a scheduled run can test.” This changes the proposition without changing its title or status. “Would need” asserts necessity, not sufficiency. Closing the two implementation gaps does not establish complete scheduling readiness. Preserve the original proposition and record its changed premises; a sufficiency hypothesis would be a separate speculative claim with its own evidence and refutation criteria.

**Unattended Agent State:** “`/scout` already matches four of the six rules” conflates a date header with a per-source read cursor and human confirmation with confirmed delivery. The six source rules also include last-moment rechecking and spend caps. Map each rule explicitly before counting matches; the current skill is structurally similar, not an implementation of four demonstrated guarantees. “The ledger is append-only” also needs a scope qualifier when applied to scout: runs append, but status cells change in place.

It also names unresolved claims, additions, and broad rewrites; “only” is not supported by the cited section. “nothing in it ever goes stale” should refer to unchanged captured bytes, not the continuing validity of their claims.

The source describes scheduled CI and claim reconciliation, not a proof that these two properties suffice. The existing speculative callout properly signals inference, but its “never with none” is too universal for the examples, and its confirm/refute criteria test quality rather than whether a gate exists. A successful ungated maintainer is unnecessary to refute a categorical claim that every unattended ingest has a gate.
