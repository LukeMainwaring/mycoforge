# How to build an agentic self improvement loop

[0:00] Hey there, I'm Ben, DevEx Engineering Lead at Warp, and I wanted to talk about self-improving agents: agents that review their own work to get better over time. This is a version of a talk I gave at AI Engineer in New York, and we'll walk through it from the lens of a software factory, which a lot of people are exploring right now. What I'm showing you here is the self-improvement loop we'll build together, but first, rewinding the clock and zooming in on the core factory loop. I want to start with some ground-setting on how software factories are defined: the way we define them and the way you could build one yourself. You may have seen a wheel like this before when talking about software factories. It's the idea of creating a centralized place where all your agent code runs, and the agents are given an assembly line of steps to complete to get work over the line. You assign work to an agent. Normally you might prompt it through Claude Code, but in a software factory, that means having a conversation with an agent on Slack, or filing an issue on GitHub, Linear, or somewhere else.

[1:12] You're taking in work through all these channels and setting up a machine of different steps the agent goes through when it picks up that task. One example might be this: an agent does triage, which means researching and checking for duplicates to make sure other agents aren't working on that task. If it requires a human to review the implementation or discuss how something should work—think "grill me," but only tagging you in when you actually need a grill-me session—that's where spec writing comes in: having an agent work with you on a plan. Otherwise, it jumps straight to implementation. This is the bulk of the agent's actions: implementing something end to end. Of course, you'll want verification. These days, this means having the agent click around what it built with computer use. That's something we'd definitely recommend, but it can also mean creating end-to-end tests with Playwright or other testing tools. Then going through rounds of adversarial code review, shipping that code, and in the best case, also having a monitor on the other side, like Sentry, to look for bug reports and file new issues to continue this cycle of agents optimizing the codebase. This is something you can implement yourself.

[2:29] There are a lot of resources on this, including one from our CEO, Zach Lloyd. But I'm going to be talking about the outer loop around this factory: the meta-engineering that goes into making sure the factory itself, this loop, runs fast and efficiently in terms of token cost. There are four steps to make sure the factory is improving itself the more work you put through it. The first is making sure all the conversations you have in a factory are stored somewhere accessible for agents to look at. That means not locking away all your conversations on your machine, but having shared storage for all the devs working on the project, so you can have an agent look through all those conversations and pull out hidden gems: failure points that should be improved in your codebase or your agent skills next time. Another core concept is scoring. This means having an agent that reviews those agent conversations. This is an LLM-as-a-judge approach, where every conversation, or a sampling of conversations, passes through another agent that receives scoring criteria to decide how well that conversation went. We'll talk about each of these. Common examples are the agent's efficiency, its code quality, and maybe its test coverage.

[3:52] Then, across all those runs, you want to isolate the failures: the runs that didn't go so well and deserve a second look to figure out how you could improve the system. On the other side, you'll have an agent aggregate all those failures, say on a 24-hour cron job, and propose improvements informed by those failures. Let me unwind that wheel into an assembly line to talk about each of those components. Starting with the agent conversations themselves, you'll want to make sure they're stored somewhere accessible, including all the runs across your entire team, not just individual machines. If you're working with Claude or Codex, this will be a folder in the root of your device—a Claude folder or a Codex folder— and all the agent traces live inside there. I've actually run into people who have every member of their engineering team upload their conversations on a cron to an S3 bucket, just so everyone's conversations live somewhere. That's a scrappy way to get started. But I'd suggest having a cloud runner where all your conversations happen. That way, all your traces naturally land in one storage mechanism, instead of everyone running agents on their own computers and trying to beam the learnings up to everyone else.

[5:18] This is a common feature of software factories: a cloud runner and a cloud machine where all this happens. The main benefit is bringing everything into one place. If you use something like Warp Factories, all those conversations end up in a shared store that you can self-host or let us host for convenience. Inside those traces, you'll want all of these components. Of course, you'll want the transcript: all the back-and-forth between the agent, its subagents, and the human in the loop. But you'll also want the tool calls and MCP calls along the way, because an agent might spin its wheels sending the wrong properties to an MCP call or reading large file diffs for too long. That should also be in the transcript so you can diagnose issues. And you'll want the outputs: the code diffs inside the transcripts themselves, or the finished PRs at a specific commit. Either way, make sure you have all three: the transcripts, the tool calls, and the code output. With this shared store of everyone's conversations, you'll want a way to score the quality of those. This is going to be pretty opinionated. It's a rubric across the metrics you care about.

[6:34] A fun example I like to ask about— obviously on YouTube, you're not going to respond to me unless this is a Dora the Explorer moment— but have you noticed that agents write too many tests? Or too many code comments? You might turn those failure points into a score that defines what you're looking for: a good conversation and output versus a bad conversation and output. One we might throw in is a redundant test score. This would define what it looks like to have a high-quality test versus a not-so-high-quality one. A common bar I reach for is Kent C. Dodds' test pyramid, which describes end-to-end tests as most valuable and unit tests as least valuable. That should be enforced in agents, and something you can test for to make sure the tests that are written are actually good. There's also Matt Pocock's idea of tautological tests. These are super brittle tests. The agent asserts that the code, as written, performs some action, like enforcing that a const always returns the same value. Obviously, that's redundant, an extreme case. But you can codify that in a markdown file describing what a tautological test looks like, and instruct the agent not to write them.

[8:00] Then you can score the agent's output based on that. We can also address the code comment problem with a verbosity score. For this, you might look at both how verbose the agent is when responding to a human, and how verbose its code comments are. They both bleed into each other. It's worth enforcing both: using simplified language, and ditching comments entirely when they're not useful. The last one definitely worth checking for is efficiency. This gets to the tool calls and MCP calls I mentioned earlier, where you want to check the agent is exploring its environment efficiently, not wasting tool calls trying to understand things. For that last one, I have a sample of what that score could look like. Here, we're encoding it as a markdown file. There are two core components to it. The first is the overall rubric that defines what we're testing against. Here, we see some common failures, like high cost to the human, with a lot of steers in a conversation, versus the agent getting it right on the first pass. And also information gathering— maybe in a test environment, and I'll show you an example of this—you have an agent trying to poke around for available port numbers before it can start verifying its work.

[9:11] That would be a failure in efficiency, where we could instruct it with skills to create the test server correctly on the first pass, instead of wasting tool calls working around problems. The second component is the rubric that grades the conversation from zero to one. Think back to grade school, when your teacher gave you a rubric that said this essay is perfect if it has five paragraphs, and a zero if it has four, or maybe you only get half marks if it uses passive voice instead of active voice—that sort of thing. Now we're enforcing it on our agents. This rubric defines, from zero to one, what efficiency and inefficiency look like. You can set a dividing line for where failure falls on this spectrum. Around the middle here, where you're looking at mostly or highly inefficient, that's a failing grade, which means the conversation deserves a second look by a self-improvement agent. Visually, this is what happens after a conversation completes. You grab the transcript for that conversation and pass it to individual scorer agents that run in their own context windows to grade that conversation according to the rubrics you've defined. Let's say there was an agent task to add a chat UI— a new chat in a mobile application, which is something we worked on recently.

[10:34] Once it completes, you'd have an LLM go through the redundant test score and decide what grade it gets. Let's say it wrote some tautological tests asserting constants that didn't deserve any testing. You might give it a failing grade and also add a few notes in the margins describing why that failure occurred: the unneeded tests on constants. Then it goes to another LLM scorer to look at the verbosity of that conversation. Let's say it didn't leave many code comments, which is good, and the PR description it output was very concise. In that case, it passes. Then for efficiency, it would look at how the agent managed its environment and tool calls, and maybe it had to flail a bit to figure out how to test the end result. It had some failing tool calls to understand its environment before it could get the test harness running. That would be a failure worth diagnosing. Then we can run through that process for all our other conversations. Over time, we'll build up a corpus of passes and failures we can hand off to a self-improvement agent, along with notes from that scoring agent. On a cron job, let's say we filter all these jobs down to just the failures, the ones worthy of the agent's time, and pass them to a self-improvement agent to look for commonalities: ways the agent typically falls over across that sample set.

[12:07] Here I'm only showing two samples, but it's best to have a large dataset before you trigger a self-improvement agent.
